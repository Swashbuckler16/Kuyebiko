# Kuyebiko — Event Ordering & Chronology Guarantees

## 1. Overview

Accurate event chronology is foundational for detecting ransomware behaviors, such as burst file mutations, rapid directory tree traversal, and high-frequency rename sequences.

This document details the ordering guarantees, concurrency boundaries, and limitations of Kuyebiko's event processing pipeline.

---

## 2. Ordering Guarantees

### 2.1 Preserved Observation Timestamps
- Every `RawFileNotification` records two timestamps upon reception from the operating system:
  1. `observed_at`: Timezone-aware UTC wall-clock timestamp (`datetime.now(UTC)`).
  2. `monotonic_ns`: High-resolution monotonically non-decreasing clock timestamp (`time.monotonic_ns()`).
- Kuyebiko **never** rewrites or replaces `observed_at` or `monotonic_ns` with processing timestamps.
- Processing timestamps and pipeline latency are tracked separately in `EventOrderingMetadata`.

### 2.2 Sequence Number Scope
- `FileEvent.sequence_number` is generated by `EventNormalizer`.
- **Scope:** Monotonically increasing integer globally scoped to each `EventNormalizer` instance.
- It reflects the deterministic normalization sequence in which events were processed and validated.
- It does **not** purport to represent absolute filesystem causality across independent physical drives or concurrent threads.

### 2.3 Single-Worker Sequential Processing
- A single background worker (`EventProcessingWorker`) consumes raw notifications from `BoundedEventQueue`.
- **FIFO within the Queue:** The worker processes items in the exact order they entered the queue.

---

## 3. Concurrency Limits & Out-Of-Order Handling

### 3.1 Multiple Watcher Threads
When multiple directory roots are monitored simultaneously:
- Independent OS worker threads invoke `ReadDirectoryChangesW` concurrently.
- Thread scheduling variations and OS buffer delivery times mean that an event from Root B observed at `T1` might enter the queue slightly after an event from Root A observed at `T1 + 1ms`.
- Kuyebiko **does not stall** the processing pipeline or introduce unbounded buffering to artificially re-sort events across threads.
- Instead, `EventOrderingTracker` tracks the latest seen `monotonic_ns` per monitored root. If a notification arrives with a timestamp earlier than a previously seen event on that same root, it is flagged as `is_out_of_order=True` and accounted for in `OrderingMetrics.total_out_of_order`.

### 3.2 Monotonic Clock Comparability
- `monotonic_ns` is valid only for durations within the same system boot session.
- It is never compared across system restarts or external systems.
- Wall-clock timestamps (`timestamp_utc`) are always normalized to UTC.
